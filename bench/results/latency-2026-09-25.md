# TTFT, ITL and TPOT: qwc vs vLLM — 2026-09-25

## Summary

- **At batch 1 without speculation we're ahead on every metric except prefill
  of a long prompt.** TPOT is 2-3.5% lower at all lengths. TTFT of a 256-token
  prompt is 28 ms vs 65. At 8k and 30k vLLM prefill is faster: 584 ms vs
  647 (+11% for us) and 2.96 s vs 3.11 (+5%).
- **With speculation k=3 on a short prompt**: 159.7 tok/s vs 144.4 for
  vLLM + MTP, TPOT 5.77 ms vs 6.56. At 8k and 30k vLLM + MTP doesn't start at all on this card,
  ours has TPOT 5.4-5.6 ms. The cost is head priming:
  +270-290 ms to TTFT on a long prompt.
- **Under load (c=32) our throughput is higher, but each request's speed
  is lower.** 1161 tok/s vs 963 (1.21x), TTFT with queue 7.4 s vs
  9.8. But vLLM's per-request TPOT is a third lower: 17.4 ms vs 26.1. The throughput lead
  compared to 17.09 (1.88x) shrank: vLLM is now measured without the vision
  tower.
- **The bench had a bug:** qwc's `servebench` counted the sample of a
  partially prefilled chunk as a token. TTFT of a prompt longer than 2048 came out as the time of
  the first chunk. Fixed; what was affected is listed below.

## Conditions

- Shared card: uvicorn (3 GB) and `index_worker` (2.4 GB), ~7 GB taken before
  start. Total budget 25 GB per engine (`--engine-budget-gb`), KV fp8, two
  interleaved rounds, the second in reverse order. Rounds agree: p50 and
  tok/s within 3%, p95 up to 6%. Tables show the mean, both values are
  in `latency-2026-09-25.json`.
- qwc — `303429d` plus the bench changes below and `servebench` changes uncommitted at measurement time
  (`--mtp-prime 2048` by default, as in `serve`;
  `language_model_only` for vLLM). Speculation — k=3, shortlist 32768.
- vLLM 0.28.0 with FlashInfer: `FLASHINFER` attention (xqa for decode),
  `FlashInferCutlassNvFp4LinearKernel`, `language_model_only`, CUDA graphs,
  prefix cache off, `max_num_seqs` = concurrency. MTP — `qwen3_5_mtp`,
  k=3. Prefill step is 2048 on short points, 8192 at 8k and 30k (vLLM's default
  on this card); qwc chunk is 2048. Both run under `nice -n 19`,
  `MAX_JOBS=4`.
- Prompts: short — `bench/corpus/serve.jsonl`, 256 tokens; long —
  concatenated `state-length` documents (`serve_decode.prompt`), the same as for
  the `serve` TTFT of 24.09. Generation is 128 tokens, `ignore_eos`.

## Definitions

The same for both engines: `bench/servebench.py` and `servebench.rs`.

- **TTFT with queue** — from submitting all requests (t=0) to the first token. At
  c=1 with eight requests that's almost entirely queue.
- **Service TTFT** — from the step that took the request into work to the first
  token. For vLLM — `first_token_ts − scheduled_ts` from the engine core clock.
- **ITL** — intervals between token emissions to a request. An emission of k tokens
  (speculation) gives interval/k. Percentiles are over intervals.
- **TPOT** — per request (last token − first)/(n − 1); percentiles are over
  requests.
- Percentile — the element at index round((n−1)·q), as in `servebench.rs`.

For vLLM the measured phase goes not through `LLM.generate` but through the same
`llm_engine.step()` loop with per-step output (DELTA): `generate` asks for
`FINAL_ONLY` and has no intervals. vLLM emission times are taken in the
frontend, after IPC from the engine core; for qwc — in-process, after copying
tokens to host.

| vLLM | 72.8 | 64.8 ms | 13.33 | 13.79 | 13.34 | 13.42 |

| vLLM | 55.6 | **584 ms** | 13.51 | 13.96 | 13.52 | 13.53 |
| qwc, k=3 + shortlist | **77.3** | 918 ms | 4.88 | 15.97 | **5.56** | 6.79 |
| vLLM + MTP k=3 | doesn't start | | | | | |

| 30k | tok/s | service TTFT p50 | ITL p50 | ITL p95 | TPOT p50 | TPOT p95 |
|---|---:|---:|---:|---:|---:|---:|
| qwc | 26.4 | 3107 ms | 13.59 | 14.07 | **13.60** | 13.65 |
| vLLM | 26.9 | **2963 ms** | 14.13 | 14.57 | 14.09 | 14.28 |
| qwc, k=3 + shortlist | **30.9** | 3400 ms | 5.03 | 20.14 | **5.44** | 6.59 |
| vLLM + MTP k=3 | doesn't start | | | | | |

- tok/s here is mostly prefill: 128 tokens vs an 8-30k prompt. What matters is
  TTFT and TPOT.
- Head priming on a 2048 window is 267-285 ms per request. That's the whole TTFT difference
  with and without speculation (+270 at 8k, +294 at 30k). The step from "What's next"
  of 24.09 — the head's linear layers in one batch instead of 256 batches of eight rows.
- Speculation on long prompts: 3.40 (8k) and 3.54 (30k) tokens per pass.
- **vLLM + MTP at 8k and 30k doesn't start at either 25 or 26 GB** (the card doesn't
  allow more: 24.0 GiB free at start). At 25 GB at 8k there isn't enough
  KV (0.93 GiB needed, 0.29 available), at 26 GB and at 30k — OOM during loading
  when allocating 2.37 GiB (the size of the bf16 vocab matrix 248k × 5120). At
  context 2048 the head added only 0.79 GiB to loading (18.65 vs
  17.86), so on long context something else ate the memory before this allocation;
  I didn't investigate the cause. Logs are in the artifact's `failed_logs`.
- The second vLLM round without MTP at 8k and 30k was taken at 24.5 GB. At 25 GB it
  failed twice during graph capture (96 MiB short): after the compile cache
  the memory profile left 2.99 GiB for KV instead of 1.35-1.51 in the first round,
  and the process hit the edge of the card. With one request the KV pool size doesn't
  change latency: 583.7 vs 584.2 ms TTFT at 8k.

## Chat: 160 requests, c=32, 256/128

| | tok/s | TTFT with queue p50 / p95 | service TTFT p50 | ITL p50 / p95 | TPOT p50 / p95 |
|---|---:|---:|---:|---:|---:|
| qwc | **1161** | **7.4 / 14.6 s** | **157 ms** | 22.9 / 23.9 | 26.1 / 26.7 |
| vLLM | 963 | 9.8 / 17.1 s | 187 ms | **16.5 / 17.2** | **17.4 / 17.9** |

- End-to-end throughput and TTFT are ours, single-request speed is theirs.
  Estimate "throughput × TPOT": we have ~30 requests in decode at once on average,
  vLLM ~17. Same as on 17.09: it holds fewer sequences
  at once, and each goes faster.
- On 17.09 it was 1165.8 vs 618.5 (1.88x, corpus, 26 GB). Our side is the same,
  vLLM grew to 963. The main difference in its configuration is `language_model_only`
  (no vision tower, +0.92 GB for KV), with a budget of 25 GB instead of 26.
  I didn't separate the contributions.
- ITL p50 on 17.09 (15.0 for vLLM vs 22.7) compared its TPOT with our ITL.
  With one definition the conclusion is the same: 16.5 vs 22.9.

## Bench: what changed

- **`servebench.rs` bug:** `execute_layout` returns a sample for every row of
  the step, and the bench counted the sample of a partially prefilled chunk as the first token.
  TTFT of a prompt longer than a chunk came out as the time of the first chunk (at 30k — 144 ms
  instead of 3.1 s), steps of the other chunks landed in ITL and inflated TPOT.
  Now a token is only decode and the prompt's last chunk. Of the published results,
  `prefill-budget-2026-09-14.md` is affected (prompt 4096, chunks 512-2048): TTFT
  there is understated by the rest of its prompt's prefill, and chunk steps landed in ITL p50
  — the "3x worse ITL" conclusion should be re-measured. The JSON in `bench/results`
  was taken at 256 tokens; it could only be affected where the scheduler split
  the prompt across steps. The `serve` TTFT of 24.09 was measured externally, from the server's
  response — this bug doesn't affect it.
- **TPOT and service TTFT** are new fields for both engines. **vLLM's ITL
  used to be TPOT**: (last − first)/(n − 1) per request, median over
  requests. Now it's intervals, as for qwc; the old vLLM `itl_ms_*` in
  `bench/results` are TPOT.
- vLLM: the measured phase is our own `llm_engine.step()` loop with DELTA, see
  "Definitions".
- JIT: the first vLLM run with FlashInfer rebuilt `fp4_gemm_cutlass_sm120`,
  `xqa` and `trtllm_utils` in the existing cache. Apparently because of a different
  `NVCC_APPEND_FLAGS` (a directory with only the curand headers); three minutes under
  `MAX_JOBS=4` and `nice`, load up to 2.2. No further builds after that.

To reproduce the point:

```
PATH=/usr/local/cuda/bin:$HOME/.venvs/baseline/bin:$PATH \
NVCC_APPEND_FLAGS=-I<directory with curand*.h symlinks> MAX_JOBS=4 \
nice -n 19 ~/.venvs/baseline/bin/python bench/servebench.py --engine vllm \
  --engine-budget-gb 25 --corpus bench/corpus/serve.jsonl --requests 8 \
  --concurrency 1 --prompt-tokens 256 --max-new 128 --context 2048
```
