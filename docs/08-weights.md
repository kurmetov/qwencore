# Загрузка весов в VRAM

`cargo run --release -p qwc-engine --bin load`

## Зачем отдельный крейт

`qwc-engine` — первое место, где встречаются три границы: кернелы
(`qwc-cuda`), чекпоинт (`qwc-model`) и планирование (`qwc-runtime`). Ниже они
друг о друге не знают намеренно: runtime остаётся CPU-тестируемым и не тянет
CUDA, а загрузчик чекпоинта — device-память.

## Принцип

Формы и имена приходят из `names::quant_linears` и `names::plain_tensors`, то
есть из compile-time архитектуры, а не из чекпоинта. Загрузчик разбирает слой
целиком и требует, чтобы каждый описанный архитектурой тензор был использован:
лишний тензор в слое — тоже ошибка, а не «неизвестное поле».

Проверки формы и типа идут до первой аллокации, поэтому чекпоинт с
расхождением падает мгновенно и не успевает занять VRAM.

## Потолок host-RAM

После каждого слоя вызывается `Checkpoint::evict_file_pages`: страницы уже
скопированы в VRAM, держать их в working set незачем. Через процесс проходит
13.7 GB, а пик резидентной памяти — **0.37 GB**. Без вытеснения mmap оставил бы
в RSS весь прочитанный чекпоинт, и движок съедал бы RAM у соседних процессов.

## Потолок VRAM

`qwc_cuda::set_memory_limit` ставится до первой аллокации; все `DeviceBuffer`
резервируют место под ним и возвращают `cudaErrorMemoryAllocation` **до**
`cudaMalloc`, если запрос не помещается. Загрузчик от этого ничего не знает:
он получает обычную ошибку CUDA и сворачивает загрузку.

## Словарные матрицы в FP8

`embed_tokens` и `lm_head` лежат в чекпоинте как `[248320, 5120]` BF16 и стоят
по 2.54 GB. Мы храним их в E4M3 со шкалой FP32 **на строку**: ровно половина
объёма, а ошибка остаётся локальной — плохо отмасштабированная строка не портит
весь словарь. В скалярном произведении шкала выносится за сумму, поэтому
lm_head применяет её один раз на строку, а не на каждый элемент.

Квантизация идёт на GPU кусками по 8192 строки через staging-буфер: держать
2.54 GB BF16 в VRAM ради конверсии незачем. После каждого куска страницы mmap
вытесняются, иначе пик host-RAM вырос бы на весь тензор (проверено: 2.69 GB
против 0.37 GB).

Три кернела в `cuda/vocab_fp8.cu`: построчная квантизация, выборка эмбеддингов
сразу в BF16 и GEMV логитов. Логиты считаются варпом на строку словаря, hidden
staging лежит в shared — без него при batch 8 трафик скрытых состояний из L2
уже превышает сами веса. Потолок одного запуска — batch 8; выше он режется на
группы ценой повторного чтения 1.27 GB.

### Чем заплатили за 2.54 GB

Измерено на настоящих весах, не на синтетике:

| | |
|---|---:|
| embed: макс отклонение от размаха строки | 3.51% |
| embed: среднее отклонение | 0.324% |
| lm_head: макс отклонение логита (2048 строк против точной BF16-арифметики) | 2.76% размаха |
| argmax на проверенном подмножестве | совпадает |

Это ещё **не** проверка качества: нужна перплексия на реальном тексте.
Если она просядет, запасной вариант — оставить `lm_head` в BF16: это +1.27 GB,
то есть фора над vLLM падает с 3.42 до 2.15 GB, но не исчезает.

## Замеры на RTX 5090

| | |
|---|---:|
| слоёв | 64 (48 linear + 16 full) |
| квантованных проекций | 496 |
| веса NVFP4 + шкалы | 13.70 GB |
| нормы, conv1d, A_log, dt_bias | 5.29 MB |
| embed + lm_head в FP8 | 2.54 GB (в чекпоинте 5.09 GB) |
| **всего в VRAM** | **16.25 GB** |
| предсказание чекпоинта по квантованным | 13.70 GB (+2 MB padding scale-layout) |
| контекст CUDA сверх наших буферов | 0.72 GB |
| пик host-RAM | 0.37 GB |
| загрузка, page cache прогрет | 2.3 s (6.93 GB/s) |
| загрузка с холодного диска | 9.2 s |

Копирование идёт из pageable mmap-памяти. Pinned staging-буфер и перекрытие
H2D со swizzle шкал ускорят прогретый случай, но на холодном старте упор всё
равно в диск.

План обещал 17.08 GB на всю загрузку. Мы держим 16.25 GB, потому что
MTP-голова (0.85 GB) пока не грузится: 16.25 + 0.85 = 17.10 GB — расхождение с
планом 20 MB.

## Что сюда пока не входит

* MTP-голова: нужна только спекулятивному декодированию;
* сам executor: таблицы указателей, CUDA graphs, token loop;
* перплексия и любые сравнения с vLLM.

## Проверка

```bash
cargo test -p qwc-engine
cargo test -p qwc-cuda --test vocab
cargo run --release -p qwc-engine --bin load
```

Тесты загрузчика не требуют GPU и чекпоинта: они проверяют, что отсутствующий
тензор назван по имени, а неверная форма отвергается до загрузки. Тесты
`vocab` требуют GPU: построчная шкала сверяется с `absmax/448`, ошибка
восстановления — с границей E4M3, выборка и логиты — с CPU-эталоном поверх уже
квантованных данных (это проверяет арифметику кернелов, а не выбор шкалы), и
отдельно проверяется разбиение batch 12 на группы.

Бинарь `load` дополнительно сверяет одну поднятую проекцию с чекпоинтом
побайтно и печатает ошибку FP8 на настоящих весах — отчёт об объёме без этого
подтверждал бы только количество занятых байт.
