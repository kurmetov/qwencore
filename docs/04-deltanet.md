# Gated DeltaNet: рекуррентный шаг decode

48 из 64 слоёв Qwen3.8 — линейное внимание с рекуррентным состоянием
`[48 голов, 128, 128]`. На каждый токен состояние читается и переписывается
целиком: при batch=32 это 21% всего трафика decode-шага, вдвое больше KV-кэша.

Готового кернела под SM120 для этого нет — это единственная часть модели,
которую пришлось писать с нуля.

## Форма рекуррентности, пригодная для одного прохода

```
S_t = a·S(I − b·k kᵀ) + b·v kᵀ  =  a·S + b(v − a·(S k))·kᵀ
o_t = S_t q                     =  a·(S q) + b(v − a·(S k))·(k·q)
```

Существенно, что `S k` и `S q` берутся **за один проход**. После этого строка
состояния уже лежит в регистрах и переписывается на месте:

```
одно чтение + одна запись   вместо   три чтения + одна запись
```

Наивная реализация делала бы три прохода: `S k`, затем `S q`, затем обновление.
При 1.57 MB состояния на слой на последовательность это втрое больший трафик
на самой дорогой после весов части шага.

## Раскладка

* варп владеет строкой состояния: 32 потока x 4 элемента = ровно 128;
* доступ вектором по 8 байт — полностью слитые 256-байтные транзакции на варп;
* блок 256 потоков = 8 варпов;
* `k·q` — скаляр, общий для всех строк, считается один раз на блок;
* строки дополнительно разбиваются между блоками по `gridDim.z`.

## Почему понадобилось разбиение строк

Первая версия ставила один блок на v-голову: `grid = (48, batch)`.
При batch=1 это **48 блоков на 170 SM** — три четверти чипа простаивало.

| | до | после |
|---|---:|---:|
| batch=1, на слой | 9.1 us | **2.7 us** |
| batch=1, 48 слоёв | 0.44 ms | **0.13 ms** |
| batch=1, % потолка | 24% | **84%** |

Разбиение корректно, потому что строки состояния обновляются независимо:
связывает их только скаляр `k·q`, который дешевле пересчитать в каждом блоке,
чем передавать между ними.

## Замеры

Потолок для чтения-записи измерен отдельно: **1408 GB/s**.
Проход идёт по 48 отдельным буферам подряд, как в настоящем decode-шаге —
гонять один буфер в цикле нельзя, он осядет в 96 MiB L2 и завысит результат.

| batch | раб. множество | на слой | 48 слоёв | GB/s | % потолка |
|---:|---:|---:|---:|---:|---:|
| 1 | 75 MB | 2.7 us | 0.13 ms | 1182 | 84% |
| 4 | 302 MB | 9.9 us | 0.47 ms | 1272 | 90% |
| 8 | 604 MB | 17.1 us | 0.82 ms | 1472 | 105%* |
| 16 | 1208 MB | 37.6 us | 1.80 ms | 1340 | 95% |
| 32 | 2416 MB | 77.5 us | 3.72 ms | 1299 | 92% |

\* выше 100% потому, что потолок мерился на раздельных буферах источника и
приёмника, а здесь строка после чтения уже в L2 и запись не требует повторной
загрузки линии.

**Кернел насыщает память: 84-95% достижимого потолка.** Оптимизировать здесь
больше нечего — остаток на batch=1 (2.7 us против теоретических 2.2 us) это
накладные расходы на запуск, которые снимаются CUDA-графами.

Результат при batch=32 — 3.72 ms на 48 слоёв — сходится с предсказанием
roofline-модели (состояние = 21% трафика шага).

## Корректность

`cargo test -p qwc-cuda --test delta_net`

* сверка с эталоном на CPU, работающим с тем же bf16-представлением состояния,
  поэтому расхождение может давать только порядок суммирования;
* допуск: выход 2e-3 (считается в fp32), состояние 1 ULP bf16 (~0.8%) не более
  чем на 2% элементов;
* отдельная проверка: при `beta = 0` запись отключена и состояние обязано
  затухать ровно в `alpha` раз — проверяется побитово.

## Что дальше

Prefill требует **чанкового параллельного скана**, а не рекуррентности:
последовательная зависимость по токенам убивает параллелизм. Это заметно
сложнее и влияет только на TTFT. Отправная точка — пример CUTLASS
`112_blackwell_ssd`.
